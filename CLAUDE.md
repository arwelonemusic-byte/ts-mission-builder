# TS Mission Builder

Web-based mission creation tool for Arma Reforger. Community members design a mission in the browser (map, factions, AI zones, briefing) and the tool generates a complete, workshop-ready mission addon as plain text files. Workbench is needed only to open the project once (regenerates `resourceDatabase.rdb` / missing `.meta`) and to publish.

Feasibility research + decisions (2026-07-04): see the report in Obsidian — `C:\Users\djdav\Obsidian Vaults\Alex's Vault\Inbox\Web-based mission making — Feasibility Report.md` (brief: `Web-based mission making.md`, foundation spec: `Mod Defaults.md`).

## Validated architecture facts (don't re-derive)

- **Offline generation works.** Addon = `addon.gproj`, `Missions/*.conf(+.meta)`, `Worlds/*.ent` (3-line `SubScene { Parent "{GUID}worlds/..." }`) `(+.meta)`, `Worlds/*_Layers/*.layer` (text, LF, UTF-8 no BOM). `resourceDatabase.rdb` is binary — never write it; Workbench recreates it on open/close.
- **Self-assigned GUIDs are accepted.** Random/timestamp 16-hex in hand-written `.meta` files works (validated in Workbench + playtest). Keep resource GUIDs stable across generator re-runs.
- **Clean resource override** = same relative path as the original + `.meta` declaring the ORIGINAL resource's GUID. For prefab overrides, mirror Workbench output (see `addons\Operation NewOp` examples): same parent ref AND same root `ID` as the original file, declare only changed components using the base's component-instance GUIDs (quoted: `SCR_Foo "{GUID}"`). Engine layers deltas — the toolkit's other components survive. Four standard overrides per mission: TS_MissionLoadouts.conf `{2B1F00FB4CED5910}` (loadout list — toolkit default is empty, all entries are new members with fresh GUIDs), LoadoutCrates_Conf.et `{897A36FA3D0A19F8}` (faction affiliation only), TS_CustomArsenal.conf `{DDDE97723E57CC62}`, Briefing.conf `{66D418A7AFBF6FEB}` (reuse the toolkit's entry instance GUIDs for the 3 default sections ids 0-2; user-added extra sections get fresh GUIDs, sequential `m_iEntryID` from 3, `m_eJournalEntryType Custom` + editable `m_sCustomEntryName` — Foxhound pattern; multi-line text = quoted lines joined by `\` + newline).
- **Component overrides in layers/prefabs must reuse the base prefab's component-instance GUIDs** — never mint fresh GUIDs for them. Fresh GUIDs only for NEW array members / nested objects.
- **Mod Defaults standard** (per spec): 6 layers (default/AO/Spawn/Markers/QRF/Props; empty `.layer` files are valid); FactionManager callsigns 1'1–1'4 + 1'6, `m_sCallsignGroupFormat "%3"`, group presets 9/9/9/9/3 on the playable faction, `m_bIsAssignedRandomly 0` on ALL factions' `SCR_FactionCallsignInfo` (default 1 hands out squad names in random order); GameModeSF spawn logic WITHOUT `m_sForcedFaction`; LoadoutManager entries Arsenal/Rifleman (names inherited from `LoadoutManager_Base.et`, set only resource + faction); Spawn layer = faction spawn point + AreaSpawn→LayerCrates/LayerVehicles slots + optional FARP `{0C16FFB1B07F4A89}` (plain placement); MVP plugin set = AIPatrol, MountedPatrol, Fortification, QRFFoot, QRFMounted, SmartGarrison. Every generated Area sets `m_bDynamicDespawn 1` + `m_iDynamicDespawnRange` = zone radius + 400.
- All catalogue GUIDs (terrains arland/eden/cain + navmeshes, faction entries, callsign infos, vanilla squad-name members, characters, vehicles, arsenal items) are ground-truthed in `generator/generate.mjs` — extend, don't re-harvest.

## Mod support (RHS)

- **Registry**: `generator/mods/rhs.mjs` exports a mod def `{id, label, workshopUrl, dependencies, factions}`; each mod faction has the SAME shape as vanilla `FACTIONS` entries except `confRef` (faction .conf resource ref) replaces `entryGuid`. `catalogue.mjs` merges mod factions into `FACTIONS` with a `mod` tag — resolvers, lib.mjs and all panels work off the one registry. Web types: `web/src/types/mission-gen.d.ts` (hand-written — update it when the registry shape changes); `factionMeta()` in `mission.ts` is the typed view for `mod`/`label`.
- **Dependencies derive from USAGE, not the UI checkbox**: lib.mjs unions `MODS[id].dependencies` for the mods of the playable + enemy factions only — a vanilla-only mission never lists mod deps even with the mod enabled. `mission.mods` (web state, migration in `loadMission`) only gates which factions the UI offers; Mission-tab checkboxes live in MissionPanel; disabling a mod cascades factions back to US/USSR (`setMods` in page.tsx).
- **FactionManager (validated the hard way)**: RHS OVERRIDES the vanilla `FactionManager_Editor.et` prefab (same path/parent/root ID), appending its factions as members with `m_bIsPlayable 0` — so RHS factions carry `entryGuid` (USAF `{5CC8DE37E1FF0F7A}`, AFRF `{5978B9CE6585BBE8}`, ION `{623962205CE2B89C}`) and mission layers override those EXISTING members exactly like vanilla factions (RHS's own Coop_CombatOps layers are the reference). Appending a fresh conf-ref member instead creates a duplicate FactionKey → deploy menu shows "no available factions" at runtime even though Workbench shows `m_bIsPlayable 1`. The `confRef` append path (CIV_ENTRY pattern, `m_bIsPlayable 0` explicit) remains in lib.mjs ONLY for future mods that don't override the prefab. ALL factions of a used mod are emitted; playable gets the standard callsign/preset block. Factions with empty `riflemen` are ENEMY-ONLY (filtered from the playable dropdown) — RHS ION is one.
- **RHS GUID harvesting (validated 2026-07-11)**: the RHS dump (`reference\RHS`) has NO `.meta` files and prefab root `ID` lines are NOT resource GUIDs (always `0000000000000001`) — folder-scanning is worthless, and reforger-item-database `data/rhs/groups.json` GUIDs are all broken for that reason (`characters.json`/`items.json` are catalog-sourced and good). Authoritative sources: `Configs/Editor/PlaceableEntities/*.conf` (groups, systems/spawn points, fortifications), `Configs/EntityCatalog/*/*.conf` (characters, vehicles, inventory items), RHS's own `Prefabs/MP/Managers/Factions/FactionManager_Editor.et` (faction conf GUIDs). Unrecoverable (excluded): USAF FORECON squad, ION URBAN CloseProtectionTeam, plain ION characters.
- RHS addon GUIDs (all three go into Dependencies): main `595F2BF2F44836FB`, Content Pack 01 `1337C0DE5DABBEEF`, Content Pack 02 `BADC0DEDABBEDA5E` (confirmed from `C:\Users\djdav\Documents\My Games\ArmaReforger\addons` folder names). Faction keys `RHS_USAF` / `RHS_AFRF` / `RHS_ION` (item-db uses `ION` + shared `FFA` pool). USAF+ION share vanilla-identical US callsign member GUIDs; AFRF has its own inline callsign object.
- Full raw harvest (superset of rhs.mjs: excluded groups, skipped vehicle variants, large base compositions, arsenal counts, unrecoverables) + provenance: `input/rhs-harvest.md`.

## Modded maps

Rolled out one at a time (validated in Workbench: Armenhof 2026-07-28, ChernarusMinus 2026-07-29, Faircroft Islands 2026-07-29, Iraq 1990 2026-07-29, Kunar Province 2026-07-29, Ruha 2026-07-29, Serhiivka 2026-07-29, Takistan 2026-07-29, Zargabad 2026-07-29, Zarichne 2026-07-29 — Kunar/Ruha/Serhiivka/Takistan/Zarichne keep their nav refs in a custom SCR_AIWorld_<Map>.et prefab instead of a GM layer; Serhiivka AND Zarichne bake a PerceptionManager into the bare world (`parentHasPerceptionManager: true`); Zargabad's GM soldier slot inherits its navmesh from a Configs/Navmesh/*.conf (follow the conf to the .nmn ref); Zargabad depends on the Takistan ADDON (map-on-map dep, transitive as usual) (grep the whole extraction for NavmeshFile); the .nmn refs slot into our navBlocks the same way. Ruha uses lowercase `worlds/` in resource paths — copy refs verbatim, never normalize case. ALWAYS grep the parent world's default.layer for baked-in managers (PerceptionManager/RadioManager/SCR_AIWorld): Serhiivka's bare world ships a PerceptionManager — set `parentHasPerceptionManager: true` on the TERRAINS entry so lib.mjs skips emitting ours (else "Duplicate entity" error). Serhiivka also ships a terrain-only Serhiivka_Empty.ent — missions parent to the FULL Serhiivka.ent like its own GM world does. Manager Y coords are unreliable ground truth (Faircroft 0, Kunar 10, Serhiivka floating) — cross-check heightmaps against terrain-fitted content entities (buildings) instead). Community maps commonly ship their own log errors (Faircroft: broken pub-sign ref, door navmesh-links; Iraq: bad ProjectileSoundsManager GUID, missing shore config) — judge a generated mission only by errors referencing OUR resources/entities. No UI gating — the terrain dropdown lists every supported terrain (vanilla first, then a disabled-option separator, then modded — `modded`/`workshopUrl` flags in terrains.ts; the Important! callout lists toolkit + map addon + enabled mods dynamically). Per-map recipe:
1. `/extract-addon` the map addon → harvest from the extracted GM world (text): SubScene `Parent` line = the bare-world ref, `*_Layers/default.layer` `NavmeshFile` lines = the 3 nav refs (soldiers/vehicle/lowres — same `SCR_AIWorld` prefab + component-instance GUIDs our generator already emits, only the file refs differ). Skip maps missing any of the 3 navmeshes.
2. `catalogue.mjs` TERRAINS entry: `parent`, `nav[3]`, `dependencies: [<map addon GUID>]` (from the workshop folder name; `58D0FB3206B6F859` = base game, never list it). List ONLY the map addon — its own deps resolve transitively (validated: ChernarusMinus pulls MinusBuildingPack/RailEnfusionRedux(→RailwayGenerator)/OutsideTerrainCore from just the map GUID). lib.mjs unions `TERRAIN.dependencies` into the .gproj deps alongside faction-mod deps.
3. Web: copy `tiles/<key>` + `heightmaps/<key>.bin/.json` from ts-ops-planner (bounds already calibrated there — `worldUR` in its maps.ts = our `worldSize`); add the `terrains.ts` entry. The dropdown picks it up automatically.
4. Junction the map addon AND its whole dep chain into the Workbench addons dir (same as RHS), generate the spike (`node generator/generate.mjs --armenhof` / `--chernarus` pattern), wb_launch + log scan, then user playtest. Large worlds: wb_open_resource may time out client-side while the world still loads fine — poll the console.log for the `Entities load` line instead of retrying.

## AI group pools

Full vanilla group catalogue lives in `generator/catalogue.mjs` `groupSets` (source: `input/ai-groups.md`), organized per faction → group set (subfaction) → size class. Size rules: **small** (sentry/MG/AT/GL/LAT/suppress/ammo/medical/sapper/engineer/recon/sniper teams) → garrison + patrols; **medium** (fire groups/teams, search groups, platoon HQs) → patrols; **large** (rifle squads, maneuver groups) → patrols + QRF (module not exposed yet). SF sets (Spetsnaz/Green Berets) reuse their squad as medium+large. Excluded: `*_Base`, `Transport`, `WithDriver`, `LessArmored`. Pool resolution = `resolveGroupPool()` (accepts multiple set keys, merges + dedupes, falls back to all sizes if a class is empty); mounted patrols use `patrolVehicles`. The mission's `enemyGroupSets` array (UI: "Enemy troops" checkbox list, min 1 selected) picks which sets to mix. Full vanilla character list for the future loadout picker: `input/characters-loadouts.md` (not yet in the catalogue).

Defense Group module (kind `slotai`, on/off only): NOT a toolkit plugin — emits a vanilla `SlotAI` child entity inside the zone's Layer (prefab `K.SLOTAI_PREFAB`, component GUID `K.CMP_SF_SLOTAI`, coords 0 0 0 = zone center; entity named `SlotAI<N>` per zone — entity names are world-global). `m_sObjectToSpawn` = the largest squad among selected enemy sets (`groupSets[*].defense` `{ref, size}`, resolved by `resolveDefenseGroup()`, ties → first selected). The slot's default 30 m defend waypoint needs no extra config. NOTE: `ZONE_MODULES[0]` is Defense Group — the fresh-zone default module in page.tsx references AIPatrol explicitly.

Fortifications module (`TS_ScenarioFrameworkPluginFortification` — singular): composition pools live in `FACTIONS[*].fortifications` `{road, roadside}` (FIA road reuses USSR's `ROAD_FORTS_USSR`); the AI pool is one `groupSets[*].sentry` team per selected enemy set, resolved by `resolveSentryPool()` (suppressed SF sets carry the parent's team, deduped). UI exposes only the budget (`maxBudget: 4` on the module def caps the input). Tuning attrs (roadside offset 15 / min road width 4 / min spacing 50 / single side) equal the plugin's class defaults and are omitted from the serialized block.

## Loadouts

Full curated character rosters live in `catalogue.mjs` `loadoutSets` per faction → subfaction (source: `input/characters-loadouts.md`; "Don't use" entries excluded; suppressed SF sets reuse parent names; USSR names are Russian by design). The UI "Loadouts" section is a checkbox multiselect over `loadoutSets[playableSubfaction]` (min 1; selection resets on faction/subfaction change; stored as prefab refs in `mission.loadouts`). Selected loadouts go into the `TS_MissionLoadouts.conf` override as `TS_LoadoutConfig` entries with fresh GUIDs (the toolkit default conf is empty — nothing to override in place). The toolkit's conf-based crate (`LoadoutCrates_Conf.et`, `TS_LoadoutSelectorConfComponent`) reads that conf locally on every machine, and the GM "Assign Loadout" action reads it directly — no replication-bubble dependency, no crate loadout override. The crate prefab is still overridden, but only to set `SCR_FactionAffiliationComponent` to the playable faction. `m_iMaxPlayers` is left at default (-1) for now — per-role player caps are a future setting (the conf supports `m_iMaxPlayers`/`m_eLimitScope` per entry when the UI adds them).

## Artillery support

Players-tab toggle + per-shell rows (HE/Smoke/Illum, 0–999) in `mission.arty`. Export flattens to `arty: {he, smoke, illum}` round counts (unchecked shell → 0) or `null` when the toggle is off. Generator (`fireSupportBlock` in lib.mjs) writes a `TS_FireSupportManagerComponent "{6995258B6DFFBB1F}"` (= `K.CMP_FIRE_SUPPORT`) override on the GameModeSF entity instance in default.layer: `m_bEnabled 1` + round counts, omitting counts equal to the prefab-effective defaults (HE 60 / Smoke 30 / Illum 30 — set in the toolkit's GameModeSF.et). `m_bEnabled` defaults to 0 in script and the prefab doesn't set it, so toggle-off = no block at all. The component has NO per-type enable flags — 0 rounds removes that round type in-game. `m_iRoundsHeavy` is intentionally not exposed.

## Markers

Markers tab (military + vanilla, mirroring ts-ops-planner's New Marker panel; no TS markers, no phonetic text substitution). Catalogue in `web/src/lib/markers.ts`: military = 48 pre-rendered PNGs (`web/public/icons/military/land-<faction>-<type>.png`, copied from ts-ops-planner), vanilla = atlas sprites (`web/public/icons/vanilla-markers.png`, CSS-mask recolored). `mission.markers` → export maps web keys to game enum tokens → `generator/lib.mjs` emits `Markers.layer` (ONE Area → ONE Layer → ONE `$grp SlotMarker.et` group with named `SlotMarkerN` bodies, Area-relative coords, fields omitted at class defaults; fixed prefab-instance GUIDs in `K.CMP_SF_SLOTMARKER`/`K.MARKER_TYPE_GUID`). **Gotchas (ground-truthed):** `m_eMapMarkerColor` (SCR_EScenarioFrameworkMarkerCustomColor) indexes the game's placed-color array by ORDINAL, so enum names ≠ rendered colors (RED renders dark red, OPFOR red, DARK_PINK dark brown — see MARKER_COLORS in markers.ts); the icon enum has no DIRECTION_OF_ATTACK_MAIN_PLANNED (that ops-planner sprite is excluded); military type is written to BOTH m_eMapMarkerType1Modifier and Type2 (they're OR-ed, both default INFANTRY), omitted for infantry, `0 0` for empty. Marker placement mode stays active for multi-drop; markers are draggable; click selects for live editing.

## Sectors (map-overlay rectangles)

Third Markers sub-tab (Military/Vanilla/Sectors, sub-tab state lifted to page.tsx as `markersTab` so map clicks can force it; RU calls sectors "Районы" — Район операции / Район задачи). No panel list — sectors are managed purely on the map (buttons + edit pane only; tab bar hides while a sector is selected). Corner handles resize with the OPPOSITE corner fixed. AI zones render purple `#9333ea` so red objectives stay distinct. `mission.sectors` = `MissionSector { kind: "ao"|"objective", x, z, length, width, rotation }` — **length spans local X** (ShapePoint X = ±length/2, `itemWorldCorners` `w`), **width spans local Z** (±width/2, `len`); max ONE `ao` (button disables; migration drops extras). Drawn by drag (pointer events, map pan suspended, min 10 m per axis, same path on touch); selectable/movable ONLY via the outline (hit layer = `fill:false` polygon with invisible fat stroke → interior stays click-through); selected sector gets 4 center-anchored corner-resize handles + a rotation handle (`drawSector` in MissionMap.tsx). AO web fill = donut polygon (world-bounds outer ring + rect hole, Leaflet's default evenodd) ≈ in-game `m_FillOutside`. Generator: appended top-level to Markers.layer (after the AreaMarkers block; valid alone) as ONE `$grp PolylineShapeEntity : K.MAPOVERLAY_PREFAB` with anonymous instances — AO = pure prefab defaults (NO component block, black outline/dark outside), objective = fixed red `TS_MapOverlayComponent` override (`K.CMP_MAPOVERLAY`); size via per-instance ShapePoint Position overrides using the prefab's fixed point GUIDs (`K.MAPOVERLAY_POINTS`, never uniform `scale`), rotation = `angles 0 yaw 0` (omitted at 0), point Y always 0. AI-zone display names are "Zone n"/"Зона n" (`zoneName` in i18n.tsx) — generated entity names stay `Area1…`.
